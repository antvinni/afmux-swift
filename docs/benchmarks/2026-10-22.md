# Benchmark, 2026-10-22

Python afm: afmux `read-mode` (script sha1 `9dec2fb3`). Swift afm: this repo,
v2, release build. macOS 27, on-device model, one run per cell (greedy
decoding makes most cells deterministic; seeded samples are too).

## Without an agent (`python3 bench/run.py all`)

- The Swift port matches Python exactly at default settings (same model,
  same greedy first attempt), and in-process calls are not measurably faster
  at this scale: generation dominates.
- `--samples 3` (MinionS repeated sampling, tests as the filter) turns the
  calendar module from fail into pass at the cost of extra model calls.
- `--split` (one job per function) hurts on its own: it broke `logline`,
  which passes whole. Not recommended.

## With an agent (Claude Opus 5.5 subagents, same prompt per task)

| task | without afm | with Python afm | with Swift afm |
|---|---|---|---|
| dates module | pass; 33,942 tokens, 3 tool calls, 19.7 s | pass, **written by the agent** (afm failed twice); 38,278 tokens, 7 calls, 46.9 s | pass, **written by afm** (`--samples 3`, attempt 3); 36,077 tokens, 6 calls, 43.4 s |
| app.log question | correct (grep); 32,033 tokens, 1 call, 6.7 s | correct, **from grep** after afm failed twice; 35,669 tokens, 5 calls, 54.2 s | correct, **from afm** (1 of 25 chunks); 34,421 tokens, 2 calls, 44.1 s |

- On these tasks the agent alone is cheapest and fastest: grep finds a log
  line for less than any afm call, and Opus writes a calendar module in one
  go. afmux's own field tests found the same for implementation (+26 %
  tokens).
- Between the engines, Swift afm completed both tasks itself where Python afm
  failed both, for fewer agent tokens and calls.
- One run per cell: treat differences of a few percent as noise.

## Read-mode review notes (Python reference)

1. A paragraph larger than a chunk is never split, so any log or file
   without blank lines becomes one chunk, overflows the context and the
   whole read exits 1 (reproduced on a 1000- and a 3000-line log).
2. One failed chunk (refusal, timeout) ends the whole read, discarding the
   answers already found.
3. Answers are cited with the whole chunk's line range, not the quote's.
4. Quote verification accepts any substring, so a one-word quote passes.
5. Reads are slow: every chunk is one model call (31 to 44 s for 36k
   tokens), so the skill's "read the file only if nothing useful comes back"
   costs real time compared with grep for exact-string questions.

Swift v2 fixes 1 to 3.
